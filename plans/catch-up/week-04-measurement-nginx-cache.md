# 第4週: 計測、nginx、キャッシュ

- 期間: 2026年9月7日（月）〜9月13日（日）
- 定例: 9月10日（木）
- ゴール: 基礎知識を接続し、「計測 → 仮説 → 一変更 → 再計測」を1周完了する

## 今週学ぶこと

### 性能指標

- レイテンシ: 1件の処理にかかる時間
- スループット: 一定時間に処理できる件数
- 並行数: 同時に処理中のリクエスト数
- エラー率: リクエストのうち失敗した割合
- 平均値だけでなく、遅い側の分布も見る
- スコアだけでなく、CPU、DB時間、エラーも比較する

### 計測の原則

- 変更前のベースラインを残す
- 原則として一度に一つだけ変更する
- 実行条件をできるだけ揃える
- スコアには揺れがあるため、必要なら複数回測る
- 改善理由を説明できない変更は採用しない
- 性能が上がってもエラーや不整合が増えたら採用しない

### nginx

- listenで接続を受け、locationで処理を振り分ける
- proxy_passでNode.jsアプリへ転送する
- 静的ファイルはNode.jsを通さずnginxから返せる
- アクセスログへ処理時間を出すと、重いパスを探せる
- keep-aliveや圧縮は仕組みを理解してから試す

### キャッシュ

- キャッシュは再計算や再取得を省き、以前の結果を再利用する
- 候補: ほとんど変わらないマスタデータ、静的ファイル、重い集計結果
- 更新されるデータには無効化条件が必要
- 利用者ごとに異なる結果を共有すると、情報漏えいや不正レスポンスになる
- 「いつ変わるか」「誰に共通か」「どこで消すか」を説明できるものだけ採用する

## 日別メニュー

### 9/7（月）— 1時間

- レイテンシ、スループット、並行数、エラー率を学ぶ
- ベンチ結果のどの数値が対応するか探す

### 9/8（火）— 1時間

- nginx設定のlisten、location、proxy_passを探す
- 静的ファイルとアプリ向けリクエストの経路を図にする

### 9/9（水）— 1時間

- キャッシュの利点と不整合の危険を学ぶ
- 過去問からキャッシュ候補を3件挙げ、更新条件も書く

### 9/10（木）定例 — 1時間

- ベンチを1回実行し、CPU、アクセスログ、slow query logを分担して観察する
- 最も時間を使っていそうな箇所について仮説を3つまで出す
- 土日に試す変更を1つだけ選び、成功条件と戻し方を決める

### 9/11（金）— 1時間

- 選んだ変更のベースラインを複数回測る
- スコア、エラー、CPU、対象処理時間を記録する

### 9/12（土）— 3時間以上

- SQLインデックス、静的配信、明らかに安全なキャッシュのいずれか1件を実施する
- 変更後に同じ条件でベンチを実行する
- 結果が悪化した場合は戻し、原因を調べる

### 9/13（日）— 3時間以上

- 再度ベンチを実行し、結果が再現するか確認する
- サービス再起動後にも正常に動くことを確認する
- 調査から採否までを改善レポートにまとめる
- 翌週の過去問演習で使う計測手順を短く整理する

## キャッシュ判断チェック

- [ ] その結果はいつ変化するか分かる
- [ ] 全利用者で共有してよいか分かる
- [ ] 更新時にキャッシュを消す方法がある
- [ ] 再起動や初期化後の状態を説明できる
- [ ] キャッシュなしの場合とレスポンスが一致することを確認できる
